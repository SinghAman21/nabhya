# Changelog — 20 July 2026

Branch: `backend` · Baseline: `b7acfdc`

Built the first working vertical slices of the platform: NGO and volunteer
onboarding wired to real persistence, superadmin monitoring, organization
"needs / offers" posting, and the public event listing with a volunteer apply
flow. Also fixed the authorization foundation that all of it depended on.

**Nothing was committed.** All changes are in the working tree.

---

## Breaking changes

### Role vocabulary unified

The server used `superadmin | volunteer | organisation` while the client used
`ngo | volunteer`, with nothing mapping between them. Canonical values now live
in `packages/shared/src/roles.ts` and both sides import them.

- `apps/native/src/store/auth-store.ts` — `UserRole` is now the shared `Role`.
- `apps/native/src/app/(ngo)/_layout.tsx` — guard compares `"organisation"`.
- `apps/native/src/app/role-select.tsx`, `src/app/index.tsx`,
  `src/components/profile-screen.tsx` — updated to match.
- The `(ngo)` route folder name is unchanged; only the role *value* moved.

### JwtGuard no longer assigns a default role

Previously every new user was force-assigned `volunteer` on their first
authenticated request, which happened during signup — defeating the role-select
screen entirely. `request.user.roles` is now empty until the user chooses, and
`AuthUser.role` is `Role | null`.

Role selection goes through `POST /api/users/me/role` and is **one-shot**:
changing it later would silently re-home an account's organization and
applications, so it requires a superadmin.

### Guest-mode backdoor removed

`setGuestMode()` in `auth-store.ts` faked an authenticated session. It was dead
code and is gone.

## Database (`packages/db`)

### New tables

| File | Tables |
|---|---|
| `schema/categories.ts` | `categories`, `organization_categories`, `user_categories` |
| `schema/events.ts` | `events`, `event_applications` |
| `schema/needs.ts` | `organization_needs`, `need_pledges` |

Design notes:

- `events.accepted_count` and `organization_needs.fulfilled_quantity` are
  denormalised so public listings avoid a per-row aggregate. Both are only
  mutated inside a transaction holding `SELECT … FOR UPDATE` on the parent row.
- `event_applications` has a unique index on `(event_id, volunteer_id)` — one
  application per volunteer per event is enforced by the database, not by an
  application-level check.
- `organization_needs.type` is `WANT` (asking for something) or `OFFER`
  (surplus to give away).
- Indexes added for the public feeds (`status + start_at`, `status + type`,
  `city`) and the superadmin verification queue.

### Changed tables

**`organizations`**
- New: `org_type` (`org_type` enum), `team_size`, `founding_year` — the
  onboarding wizard was already collecting these and throwing them away.
- New: `rejection_reason`, `reviewed_by`, `reviewed_at` for the review trail.
- New: unique index on `owner_user_id`, so a double-submitted onboarding form
  cannot create a duplicate NGO.
- New indexes on `verification_status` and `city`.

**`users`**
- New: `bio`, `city`, `state` (volunteer profile), `suspended_reason`,
  and `onboarded_at` — the completion signal for volunteers, who have no
  organization row to check.

### Relations

Reverse relations added on `organizations` (`events`, `needs`,
`organizationCategories`) and `users` (`ownedOrganizations`,
`organizationAdmins`).

Deliberately **not** added: `users → eventApplications / needPledges`. Those
tables reference `users` twice (actor + reviewer) and Drizzle cannot
disambiguate without `relationName`. Query them from the child side. The same
pre-existing ambiguity affects `users → userDocuments`.

### Seed

`packages/db/src/seed.ts` now seeds 10 cause categories alongside the three
roles, and reports counts.

### Common infrastructure

- `common/audit/` — `AuditService` + global `AuditModule`. The `audit_logs` table

### Authorization and integrity rules

- Every organisation-scoped route resolves the org from the token via
  `OrganizationsService.requireOwnedOrganization` — an organization id is never
  accepted from the client. `requireVerifiedOrganization` additionally gates
  anything that becomes publicly visible, so an unverified NGO can draft but not
  publish.
- Public list endpoints inner-join `organizations` and filter on `VERIFIED` +
  `ACTIVE`, so unverified or suspended NGOs never surface (and pagination counts
  stay correct, which a post-filter would break).
- Accepting an applicant re-checks capacity inside the transaction against a
  locked event row — two admins reviewing simultaneously cannot overfill.
- Withdrawing after acceptance frees the seat. Re-applying after withdrawing
  reuses the existing row so the unique index still holds.
- Deleting an event with accepted volunteers **cancels** it instead; deleting a
  need with accepted pledges **closes** it. The record of what people committed
  to is never erased.
- Suspending an organization cancels its published events and closes its open
  needs, so volunteers stop seeing and applying to them.
- Verifying an identity document promotes the user's own `verification_status`.
- A superadmin cannot change their own account status.

# Session 2 — remediation and file storage

Follow-up work after auditing the first pass. **Uncommitted** — no commit
authorisation was given for this session.

## Critical fix: dependency injection was silently broken

Every controller and service introduced in session 1 had `undefined` injected
dependencies. The app booted cleanly and registered all 50 routes, but any
request touching a service would have thrown `Cannot read properties of
undefined`.

Cause: `apps/server/tsconfig.json` sets `emitDecoratorMetadata: true`, but the
dev runner (`tsx`) and the bundler (`tsdown`) both use esbuild, which does not
implement it. `design:paramtypes` was therefore always `undefined`, so Nest saw
classes with no declared dependencies and constructed them with no arguments.

Session 1 never hit this because the original code sidestepped it entirely —
guards used `@Inject(Reflector)`, services used `@Inject(DB_TOKEN)`, and the one
controller had no constructor at all.

Fixed by adding explicit `@Inject(Token)` to every constructor parameter across
9 controllers and 7 services, and reverting the type-only service imports that a
linter autofix had introduced (`verbatimModuleSyntax` erases those, which breaks
injection a second way).

Guarded by `apps/server/scripts/verify-di.ts` (`pnpm --filter server verify:di`):
it boots the container, resolves all 20 injectable classes, and fails if any
constructor-assigned property is undefined. Verified to actually fail by
removing an `@Inject` and confirming a non-zero exit.

## Bug fixes

- **Onboarding "skip verification" looped.** It routed to `/(volunteer)`, but the
  role is `organisation`, so that layout redirected to `/`, which found no
  organization and sent the user back to onboarding. Now routes to the public
  `/events` feed, which requires no role. Removed the misleading `isSkipped`
  store state, which claimed `isOnboarded: true` against server truth.
- **Pledges never carried a quantity**, so `fulfilledQuantity` advanced by zero
  and a need could never reach `FULFILLED`. Added `PledgeSheet` to collect
  quantity and message, with a remaining-amount check; the server now rejects a
  quantity-less pledge against a quantified need.
- **Organisations could not review pledges at all.** Added `PledgesSheet`
  (accept / reject / mark received), opened from the needs list.
- Applicant and pledge review now collect a `reviewNote`, which volunteers were
  already being shown but which was always empty.

## File storage — Cloudflare R2

`apps/server/src/common/storage/`: a `StorageProvider` interface with a real
`R2StorageProvider` (S3-compatible presigning) and a `StubStorageProvider` used
when credentials are absent. The stub keeps every upload path exercisable
locally and is refused in production.

Flow: `POST /api/uploads/intent` returns a pre-signed ticket → client PUTs the
bytes directly to R2 → client submits the object **key**. Bytes never pass
through the API. Signatures pin Content-Type; size is verified with a HEAD in
`assertUploaded` before any key is persisted.

Keys encode their owner (`org-documents/{orgId}/…`), which is what authorises
downloads via `POST /api/uploads/download-url` without trusting the client.

Renamed `documentUrl` → `documentKey` (and `document_url` → `document_key`)
across the schema, shared contracts, services and client, since these now hold
object keys rather than URLs.

# Session 3 — engagement, certificates and donations

Continuation of the same build. **Still uncommitted.**

## New domains

**Schema** — `engagement.ts` (`bookmarks`, `reviews`, `notifications`),
`certificates.ts`, `donations.ts`, plus `attended_at` on `event_applications`.

**Notifications** — in-app only, one row per recipient so read state and the
unread badge are plain queries. Global module; emitted fire-and-forget from
application review, pledge review, review replies, certificate issuance and
completed donations, so the inbox is populated by real activity rather than
being a screen with nothing in it. Superadmin broadcast fans out in chunks.

**Bookmarks and reviews** — idempotent bookmark toggle guarded by a unique
index. One review per person per organization; a second submission edits the
first. Owners cannot review their own NGO. Rating summary returns the average
plus the 1–5 distribution in a single scan.

**Attendance and certificates** — attendance is an explicit action, not
inferred from the event end date, and it gates issuance: a certificate cannot
exist for someone who did not turn up. Un-marking attendance is refused while a
certificate exists. Both delivery forms are built: a public verification route
(`GET /api/certificates/:code/verify`, no auth — the point of a code is that a
third party can check it) and a `pdf-lib` PDF stored in R2. The record is
written before the PDF renders, so a storage failure leaves a recoverable
`pdfKey: null` rather than losing the certificate.

**Donations via Dodo Payments** — I checked Dodo's live API docs rather than
working from memory, which surfaced two things worth knowing:

- Dodo is **product-based**: `POST /payments` takes a `product_cart`, not a
  free-form amount. Variable donations are modelled as N units of a ₹1 donation
  product, so amounts are whole rupees. Set `DODO_DONATION_PRODUCT_ID`.
- Webhooks follow the **Standard Webhooks** spec: HMAC-SHA256 over
  `{webhook-id}.{webhook-timestamp}.{raw body}`, base64. Implemented with a
  timing-safe comparison and a 5-minute freshness window. `NestFactory` now runs
  with `rawBody: true`, because a re-serialised JSON body would never verify.

Money integrity: amounts are integer paise, never floats. A donation is created
`PENDING` with a server-computed amount and only a verified webhook can complete
it. `provider_payment_id` is unique and completion is guarded on the row still
being `PENDING`, so a webhook replay cannot double-count. A mismatch between the
webhook amount and the stored amount is rejected outright. Anonymity is applied
in SQL, not the client.

Same stub pattern as storage: absent `DODO_*` credentials fall back to a fake
provider so the flow stays testable, and production refuses to start without
real ones — taking money that goes nowhere is worse than not starting.

# Session 5 — backend hardening

Rigorous pass over the backend: tests written to find defects rather than
confirm behaviour, plus production hardening. **117 tests, up from 46.**

## Defects found and fixed

**`GET /api/admin/users` threw a 500 on every call.** The `roles` aggregate used
an interpolated column inside a correlated subquery, which Drizzle renders
*unqualified*, making `"id"` ambiguous between `user_roles` and `roles`. The
whole superadmin people list was unusable. No test had ever called it.

**Three more subqueries silently returned zero.** Same root cause, but without
an error: an unqualified `"id"` binds to the subquery's own table, so the
comparison was table-to-itself and always false.
- `events.pendingApplications` — the NGO events screen permanently showed "No
  new responses" even with applicants waiting. An organisation would never know
  anyone had applied.
- `needs.pendingPledges` — same for donation offers.
- Admin `pendingDocuments`, `eventCount`, `needCount` — every NGO row in the
  verification queue read zero.

Silent wrong answers are worse than crashes, and typecheck cannot see them.
All four are now hand-written with table-qualified SQL and pinned by tests.

**Proximity search reported the page size as the total.** `listNearby` passed
`rows.length` as the count, so `totalPages` was always 1 and nobody could reach
page 2. Also removed a needless `groupBy`/`having` — the distance filter belongs
in `WHERE`, which lets the count query reuse the identical predicate.

**The exception filter discarded field-level validation errors.** It extracted
`message` and dropped `errors`, so every form received "Validation failed" with
no way to mark the offending input. Now forwarded, with 4xx logged at warn
instead of error (a stack trace per failed validation buries real 5xx), and
internal failure details never surfaced to the caller.

**The latitude index my own comment claimed existed did not.** Added.

## Hardening

- **Readiness probe.** `GET /api` was a hardcoded `"OK"`, so a load balancer
  would route traffic to an instance whose database was unreachable. `GET
  /api/health` now queries the database and reports which storage provider is
  live — catching "running on the stub" before documents vanish.
- **Rate limiting** via `@nestjs/throttler`: 120 req/min default, 10/min on
  reviews and donation checkout, 20/min on upload tickets. The guard runs
  *before* auth so a flood costs no JWT verification or database round trip.
  Webhooks and health probes are exempt — a 429 on a provider retry loses a
  payment confirmation we cannot reconstruct, and on a probe reads as unhealthy.
- **`trust proxy`**, without which every request shares one rate-limit bucket.

  but nothing could invoke it.
