% ------------------------ ABSTRACT ------------------------
\begin{abstract}
Nabhya is a mobile-first platform that has been created to connect verified non-governmental organisations (NGOs) in India with volunteers and donors. It focuses on two battles in digital philanthropy: it can be difficult to determine whether to trust an organisation, and it is uncertain what kind of help an organisation might need at the moment. An NGO uploads its legal documents to Nabhya, and a superadmin examines them before anything the organisation posts is made available to the public. After verification, the NGO may post volunteering events and item-level needs, either as a WANT or as an OFFER of surplus resources, and it can post updates to a community feed. Volunteers can discover organisations and opportunities, apply to events, pledge items, bookmark and review organisations, monitor their impact, and receive a certificate of participation that can be verified online with a verification code. Monetary donations have been implemented, but they are on hold pending a go-live decision.

\noindent \\ The system uses an Expo/React Native app, a REST API built with NestJS, PostgreSQL on Supabase (via Drizzle ORM), Supabase Auth (for sign-up and login) and Supabase Storage (for files). Zod schemas are shared between the app and the server, which means that both validate data in the same way. Security and data integrity were given special consideration. Its features include role-based access control, public lists restricted to verified organisations, transactional counter updates, signed upload URLs, webhook-based payment settlement and integration tests that run against the committed migrations. Only implementation and integration testing are evaluated. We have not conducted a user study or measured production-scale performance, so we cannot make any claims regarding either.
\vspace{0.15in}

\noindent\textbf{Keywords:} NGO platform, volunteer management, digital philanthropy, item donations, verification, React Native, NestJS, PostgreSQL, role-based access control
\end{abstract}

\chapter{Introduction}
\label{ch:introduction}

\section{Background and Motivation}
Civil society organisations need the volunteer work of people as well as material and financial contributions. A potential good Samaritan is likely to ask two questions before stepping in: can I have confidence in this organisation, and what can I do for it at this moment? A simple listing on a website only tells part of the story when it comes to the first question. The second one doesn't usually come up on event platforms, since they can't identify a particular material need or a surplus that someone else could use.
We want to answer both with Nabhya, a mobile-first system that integrates organisation verification, volunteering opportunities and giving of individual items in a single location. Public discovery co-exists with logged-in workflows, and the superadmin role manages verification, moderation and auditing.

\section{Problem Statement}
We wanted to create a secure, mobile-friendly platform on which verified NGOs can post volunteering opportunities as well as material needs, while citizens can search for organisations, offer their time or items, and receive a certificate of participation that others can verify. The platform also needs administrative tools for verification, moderation and auditing.

\section{Objectives}
The objectives of Nabhya are:
\begin{itemize}
  \item Provide document-based onboarding and verification for NGOs, and identity-document handling for volunteers (Sections~\ref{sec:impl-auth} and~\ref{sec:impl-verification}).
  \item Support the full event lifecycle: drafting, publishing, applications, review, attendance and completion (Section~\ref{sec:impl-events}).
  \item Represent item-based support through WANT and OFFER listings, with quantities and fulfilment tracking (Section~\ref{sec:impl-needs}).
  \item Show only verified and active organisations in public discovery.
  \item Offer bookmarks, follows, reviews, organisation replies, announcements, financial reports, a community feed and notifications (Sections~\ref{sec:impl-engagement}, \ref{sec:impl-feed} and~\ref{sec:impl-notifications}).
  \item Issue attendance-based certificates that can be downloaded as PDFs and verified publicly by code (Section~\ref{sec:impl-certificates}).
  \item Support monetary donations settled through a payment-provider webhook, which is currently on hold for go-live (Section~\ref{sec:impl-donations}).
  \item Protect data integrity through access control, audit logs, rate limiting, database constraints and automated integration tests (Chapter~\ref{ch:testing}).
\end{itemize}

\section{Scope of Work}
Nabhya consists of an Expo~\cite{expo}/React Native~\cite{reactnative} mobile app, a NestJS REST API, a PostgreSQL database, hosted authentication, object storage, workflows for each role, public feeds and administrative tools. The mobile app has separate route groups for volunteers, organisations and superadmins. A dedicated web application for the admin console, email and push notifications, and full pagination on the client are left for future work (Sections~\ref{sec:limitations} and~\ref{sec:future}).

\section{Development Methodology}
The project was set up as a TypeScript monorepo, using pnpm workspaces and Turborepo (Table~\ref{tab:monorepo}). The database access layer, the environment validation and the request and response contracts are packaged together as shared packages. We began by building features around a full API and client workflow, and then applied schema migrations and automated integration tests to make sure all components stay in sync. This is an inventory report on the current state of the repository. It does not include a user-adoption study or a scale-up evaluation.

\section{Feasibility Study}
\label{sec:feasibility}
\begin{description}[leftmargin=0pt, itemindent=0pt, labelsep=0.4em, font=\bfseries]
  \item[Technical feasibility:] Every piece of the stack we chose is proven at the scale a pilot NGO platform needs: Expo and React Native for a single cross-platform client, NestJS for a typed, modular API, and managed Postgres/Auth/Storage through Supabase so the team was not operating its own database or identity server. Building 75{,}000+ lines of working TypeScript across the mobile app, the API and the shared packages (Section~\ref{sec:effort-estimation}) over the project timeline is itself evidence that the approach was technically workable for a three-person team.
  \item[Operational feasibility:]Nabhya makes a process that NGOs and volunteers already do, automatic. run by hand - checking an organisation's paperwork; posting a volunteering opportunity, Who turned up and what a shelter requires this week. There are no additives in the product. Invites a volunteer to an NGO coordinator to adopt a new mental model; roles, the verification step and the WANT/OFFER language map onto what they do on. paper, via WhatsApp or via a general application. That reduces adoption costs When it comes to changing an NGO's process to conform to the software, it's relative.
  \item[Economic feasibility:] The stack is almost completely usage based managed services. These three (Supabase, Vercel, Render) have free or low tiers that easily accommodate a pilot's traffic, and No fixed costs of carrying out before there are actual organisations on the platform. There's only one recurring paid dependency with transaction prices – Razorpay; that cost only shows when a donation is actually spent - is proportional to use, not actual donation - being a fixed overhead.
\end{description}

\section{Effort Estimation}
\label{sec:effort-estimation}
We sized the project after the fact with the COCOMO Basic model~\cite{boehm1981} so the report carries a standard estimate alongside what we actually measured, rather than one or the other. The codebase stands at 75{,}087 lines of TypeScript, or 75.1 KLOC, measured directly from the repository: 55{,}474 in \texttt{apps/native} (the mobile client), 15{,}030 in \texttt{apps/server} (the API), 2{,}368 in \texttt{packages/db} (schema and migrations) and 2{,}215 in \texttt{packages/shared} (the Zod contracts).

\noindent \\ For an organic project, COCOMO Basic gives effort $E = 2.4 \times (\text{KLOC})^{1.05}$ person-months and schedule $D = 2.5 \times E^{0.38}$ months. At 75.1 KLOC this works out to $E \approx 223$ person-months and $D \approx 19.5$ months, implying a team of roughly 11-12 people working full-time. The actual project was three students working part-time around coursework over the five months in Figure~\ref{fig:timeline}, which is a small fraction of the COCOMO figure. We read that gap as the model, not the team: COCOMO Basic was calibrated on 1970s-80s organic software projects written largely by hand, and it has no term for a scaffolded monorepo, a schema-driven ORM, shared Zod contracts generating both client and server validation, or AI-assisted code generation, all of which cut the person-hours a line of delivered code actually costs today. We report the COCOMO number because estimating effort is expected of this report, not because we think it reflects how long the project would take a typical team to build with the same tools.

\chapter{Literature Survey}
\label{ch:literature}

\section{Existing Digital Volunteering and Donation Platforms}
People are already using online platforms to locate social organisations and volunteering opportunities. We see two gaps in the project documentation: first, trust in the organisation, and second, giving that people can act on at the level of individual items. Nabhya answers the first with a review-based verification workflow. For the second, it treats material needs as records in their own right, rather than as secondary to participation or money transfers. A summary of the comparison is given in Table~\ref{tab:comparison}.

\section{Document-Based Verification and Moderation}
A verification workflow offers independent, document-based verification before an organisation's registration goes public. In Nabhya, organisations hand in their legal documents and a superadmin looks into them. Public queries only return organisations whose verification status is \texttt{VERIFIED} and whose operational status is \texttt{ACTIVE}. This rule is enforced in the server-side query and does not depend on the client app's UI (see Section~\ref{sec:impl-verification}).

\section{Event Lifecycle and Concurrency}
Managing an event isn't just about keeping track; it is about the entire event lifecycle. Applications may be accepted or rejected, attendance must be recorded, and the number of accepted volunteers must not exceed the event's capacity. Counters are modified within database transactions that use row-level locks, and a unique constraint ensures that a volunteer cannot register twice for the same event. These safeguards are very important when several different requests try to modify the same event at the same time (see Section~\ref{sec:impl-events}).

\section{Item-Level Need Matching}
The WANT/OFFER model is applicable in both directions of exchange, which yields item-level need matching. A WANT is a request and therefore a need of the organisation, while an OFFER is a surplus that someone else might want. Pledges include the amount pledged, the review process and the completion of the pledge. A denormalised fulfilled-quantity field allows for quick listings, while every change is treated as a transaction, which keeps the number current (see Section~\ref{sec:impl-needs}).

\section{API, Data and Validation Technologies}
A resource is made available to the outside world through a REST API over HTTP. With NestJS~\cite{nestjs} we get modular controllers, dependency injection, guards and validation pipes. Relational constraints and transactions are provided by PostgreSQL~\cite{postgresql}, and typed queries are generated from the schema by Drizzle ORM~\cite{drizzle}. The same Zod~\cite{zod} schemas are used for the client forms and the server validation, which helps prevent the two from disagreeing about what is valid data. The complete technology stack is given in Table~\ref{tab:stack}.

\section{Authentication, Storage and Payments}
Supabase Auth~\cite{supabase} generates identity tokens~\cite{jwt}, which the API then checks against a remote JWKS endpoint~\cite{jwk}. Uploaded files are stored in Supabase Storage~\cite{supabase}. Pre-signed URLs are short-lived URLs that the client can use to send and receive files without the file contents ever passing through the API. Settlement only occurs through signature-verified provider webhooks (Razorpay~\cite{razorpay}).

\section{Testing Approach and Research Gap}
Our tests are performed with Vitest~\cite{vitest} and PGlite~\cite{pglite}, an in-process, PostgreSQL-compatible database constructed from the committed migrations. This allows the tests to exercise unique constraints, aggregates and row locking against real SQL. What this project offers, and what was missing, is a single platform that supports organisation discovery, volunteering and item-level exchange and also enables publicly verifiable participation credentials, all through a mobile-first point of entry.

\section{Interaction Design Approach}
\label{sec:lit-interaction-design}
Most volunteering and donation apps we looked at reuse a single interface idiom - a scrollable list of cards - for every screen in the product, including the operator-facing ones. That works for browsing, which is what a volunteer mostly does, but it works badly for the task an NGO coordinator or a platform administrator actually has: scanning, sorting and acting on dozens of rows at once. Nabhya treats "browse" and "operate" as genuinely different interaction modes rather than re-skinning one component for both. The volunteer-facing surfaces (Section~\ref{sec:impl-ui}) stay card-based, but a card's \emph{shape} - not a colour tint - is what tells a need apart from an event or a story, because colour collapses in greyscale and says nothing in a feed where forty consecutive rows share a kind. The organisation and superadmin surfaces (Sections~\ref{sec:impl-admin-console} and~\ref{sec:impl-ui}) drop the card metaphor entirely in favour of sortable, filterable tables with bulk actions, which is closer to how an operator-facing admin tool is conventionally built than to how a consumer feed is built.

\section{Important Database Decisions}
The \texttt{events.accepted\_count} and \texttt{needs.fulfilled\_quantity} fields are denormalised counters. Unique constraints are used to enforce the rules that matter most: only one application per volunteer per event, one certificate per event application, one follow and one review per user and organisation pair, and one bookmark per user and organisation pair.

\section{Team Management and Collaboration}
\label{sec:impl-team}
An organisation account is either the team's owner or a member who joined through an invite, and four rules keep that distinction coherent end to end. Accepting an invite is what actually makes an account an organisation account: it grants the role to a volunteer-free account, refuses one that already holds the volunteer role (a role, once chosen, routes the client permanently and is not meant to be swapped), and refuses anyone already on a team, since \texttt{organization\_admins}' partial unique index caps a person at one active membership. Onboarding-status check doesn't check for ownership, so as long as someone joined the organisation since the organisation was founded, they should appear in the organisation app, but a suspended organisation's status is shown to any member of the organisation, not just to its owner. The notification of verification is sent to the entire team, not just the account that submitted documents: If the account is rejected or approved, this is a fact about the organisation not about the person who submitted the documents. Any member action which is publicly visible (publishing a post, editing a live event, posting a comment to a review) is re-checked against that member's team role on the server, rather than derived from who created the organisation, with role seniority (\texttt{OWNER}/\texttt{ADMIN}/\texttt{MANAGER}/\texttt{MEMBER}/\texttt{VIEWER}) derived from the \texttt{organization\_admins} list.

\section{Event Management and Applications}
\label{sec:impl-events}
Organisations plan events with a particular venue, time, application closing date and a fixed number of volunteers for the event. An event moves through the stages draft, published, cancelled and completed. Volunteers make applications and may withdraw, and organisations go through the applications and record attendance. A unique constraint on the event and volunteer pair prevents a volunteer from applying twice for a particular event. Once an application is accepted, the API increments the event's accepted counter within a transaction that acquires the event row lock, thus ensuring that the capacity is not exceeded even when requests are concurrent (Figure~\ref{fig:sequence-event-application}).

\section{Needs and Item Pledges}
\label{sec:impl-needs}
The needs module supports two types of listing. A WANT is an organisation's request for a quantity of some resource. An OFFER states the items an organisation has in surplus that others can take. A user makes a pledge against a listing, which the organisation can accept, reject or complete. Each need keeps its urgency, expiry, status and fulfilled quantity, and row-locking transactions ensure that the fulfilment counter is not altered by another transaction at the same time. Figure~\ref{fig:needs-management} shows the organisation-side needs dashboard.

\section{Engagement and Public Information}
\label{sec:impl-engagement}
The engagement layer covers bookmarks, follows, reviews, organisation replies and in-app notifications. Organisations can also add and publish public announcements and financial reports. Duplicate bookmarks, follows and reviews are not allowed, because of unique constraints. When an announcement is published, it notifies the users who have bookmarked the organisation. Financial reports are kept separate from the private verification documents and are public by design.

\section{Community Feed}
\label{sec:impl-feed}
The feed is built on a unified posts table, with media attachments, interactions (likes, saves, shares and impressions) and comments, as listed in Table~\ref{tab:entities}. The volunteer home screen (Figure~\ref{fig:volunteer-home}) and the organisation feed (Figure~\ref{fig:organisation-feed}) show verified organisation updates and community posts. The composer that creates a row writes it through whichever endpoint actually owns that row type - an update through the feed endpoint, a need through the needs endpoint, an event through the events endpoint, an announcement through the announcements endpoint - rather than writing every kind through one shared posts call and varying only a tag, which is what let a mistagged row reach the ranking service with the wrong shape in an earlier version of the schema (Section~\ref{sec:deepdive-feed} covers how the three ranked views score the result). The card that renders a feed row is told apart from the others by its arrangement rather than by colour: an event indents its date into a left column, a story leads with its photo, a need ends with a facts block showing the remainder still needed and a progress bar, and an update is left as plain text, so a reader can tell the four kinds apart at a glance even in greyscale, and a brand colour is reserved for exactly the two places that should draw the eye - a need's progress bar and its one solid call-to-action button.

\section{Upload and Object Storage Workflow}

\section{Certificates and Participation Verification}
\label{sec:impl-certificates}
A certificate is linked to a volunteer's event application and to the organisation, and it can only be issued after attendance has been recorded. Every certificate record contains a unique public code, the PDF object key, the issuer and any revocation information. The volunteer downloads the PDF using an authorised signed URL from Supabase Storage (Section~\ref{sec:impl-uploads}). A public verification endpoint makes it possible to check a certificate code without having an account. A revoked certificate will still resolve, but it will be marked void. \section{Monetary Donations}
\label{sec:impl-donations}
The data model supports donations from registered users as well as from guest donors. The server determines the amount and stores it as an integer number of paise. \\ The client cannot mark a donation as successful by itself: a donation starts in the \texttt{PENDING} state and is completed only when a signature-verified webhook from the payment provider (Razorpay~\cite{razorpay}) is received. \section{Notifications, Audit and Administration}
\label{sec:impl-notifications}
The notification system stores in-app messages for application and pledge outcomes, verification events, certificates, donations, reviews and broadcasts. A broadcast creates one notification row per user, so each person keeps their own read state. Administrative actions and other sensitive operations go into an append-only audit log that records the actor, the action, the entity, the old and new values and the IP address.

\section{Superadmin Console}
\label{sec:impl-admin-console}
The superadmin screens are deliberately not the volunteer feed's card layout reused with extra buttons - they are a data console, because the task at hand is scanning and acting on rows, not browsing a feed. The organisation directory and the volunteer directory are full-width sortable tables with a table/cards switch, a pinned command bar above them, and multi-axis select filters rather than the feed's single search box, and the two directories deliberately never merge into one screen: \texttt{organizations} and \texttt{users} filtered to the volunteer role are two different populations, and an NGO's own user account is reached from its organisation's dossier, not from a role filter that spans both. Every list exposes server-side \texttt{sort} and \texttt{dir} parameters with a stable tiebreaker column, so paging a low-cardinality sort - most organisations share a handful of verification statuses - can never silently repeat or skip a row between pages. The cross-org document verification queue supports bulk review: a batch of documents is reviewed sequentially rather than in one transaction, so a single malformed document in a batch of forty fails and is reported on its own without rolling back the other thirty-nine decisions, and each document re-derives its owner's overall verification status from the full document set (Section~\ref{sec:impl-verification})

\noindent None of these pieces is load-bearing on its own - a reviewer can swap \texttt{amount-field} for a different control without touching \texttt{event-fields} or \texttt{need-fields}, and a new post type can be added by writing one new \texttt{*-fields} file and wiring it into \texttt{composer-bar} rather than editing a shared switch statement that every other post type also depends on.

\noindent The same codebase runs on both a phone and a desktop browser through React Native Web, and the feed card's responsive behaviour - whether action labels are shown beside their icons, how tall a photo or video is allowed to grow, whether the layout runs compact - comes from one shared \texttt{useMedia()} hook that reads the window size, rather than from component-local breakpoint checks scattered through the card and composer files. Centralising it there was also what avoided a second measurement loop: because \texttt{useMedia()} only reads the window and never a measured element's own size, it cannot feed back into the layout it helps decide, which is the same class of bug Section~\ref{sec:impl-ui-conventions} describes for the card's media block.

\noindent \\ Three rendering rules exist specifically because getting them wrong once already broke something, and each is worth stating with its reason rather than just as a convention. First, only the card's media block measures its own size (a single \texttt{onLayout}); an earlier version let the card shell measure itself to cap media height, which on the web created the feedback loop shown in Figure~\ref{fig:measurement-loop} - the card's measured width set the media height, the media height changed the page's scroll extent, and the resulting scrollbar changed the card's own width back, which React's reconciler eventually reported as \emph{Maximum update depth exceeded}.

\noindent Second, hover state is read directly from the pressable's style callback (which React Native Web already passes a \texttt{hovered} flag into) rather than held in a \texttt{useState} hook, because a hover hook re-renders the card on every pointer movement, and a card showing a video player cannot afford to re-render each time a cursor crosses one of its four action icons. \noindent Media follows a comparable set of small, deliberate rules. A card's attached photo or video is capped by \emph{height}, not width - the carousel is given a maximum height and raises its tile's aspect ratio to whatever respects that limit, letting the image crop rather than letting a tall 4:5 photo push a desktop card's own like button off the bottom of the viewport. Nothing autoplays: a muted preview only begins playing once its card is the one the reader has opened full-screen, because starting a video unasked spends a reader's mobile data for nothing. Every icon-only control - the four actions beside a card's primary button - carries its own \texttt{accessibilityLabel}, and like and save additionally report their pressed state through \texttt{accessibilityState.selected}, so a screen reader announces "liked, button" rather than a bare, stateless "button" on a control whose entire purpose is to toggle.

\noindent None of these conventions is enforced by a linter; they hold because each one is written down next to the code it governs rather than only in a design document a contributor would have to go looking for separately. That is a deliberate trade-off worth stating plainly: a rule documented beside its implementation is read by the person about to break it, at the moment they are about to break it, in a way a separate style guide rarely is - and the cost is that the rule has to be re-stated, as it is here, rather than living in exactly one place.

\section{Guard Pipeline}
\label{sec:guard-pipeline}

None of the three is opted into per route; a new endpoint is protected the moment it exists, and a route only becomes public or rate-limited differently by explicitly saying so with a decorator. \section{Authentication: JWT Verification and Identity Sync}
\label{sec:jwt-internals}
The \texttt{JwtGuard} verifies the bearer token's signature against Supabase's own JWKS endpoint using the \texttt{jose} library's \texttt{createRemoteJWKSet} and \texttt{jwtVerify} - the API never holds or checks against a shared secret, only a public key it fetches and caches from Supabase. This is why Supabase Auth must be configured for asymmetric signing (ES256/RS256); the JWKS endpoint that makes remote verification possible does not exist under the older shared-secret (HS256) signing mode, and Section~\ref{sec:setup-guide} flags this as the first thing to get right when standing up a new environment.
\clearpage
\noindent On every verified request, not only at login, the guard checks the matching user's account status and rejects a \texttt{SUSPENDED} account even if its token is still technically valid - a suspension takes effect immediately rather than waiting for the token to expire. The guard also just-in-time syncs the Supabase identity to our own \texttt{users} row: it looks the user up by \texttt{auth\_user\_id}, falls back to matching by e-mail and linking the two records if Supabase's id is new but the e-mail already exists, and otherwise inserts a fresh row. The authenticated user's roles are attached to the request sorted by a fixed priority order (superadmin, then organisation, then volunteer) specifically so that a user holding more than one role does not get a different "primary" role depending on query order - that kind of flip-flop is exactly what caused the client-side redirect loops noted as a historical bug in Section~\ref{sec:impl-auth}.

\noindent \\Two decorators soften this otherwise deny-by-default behaviour. \texttt{@Public()} removes the check entirely for genuinely open endpoints such as the public event feed. \texttt{@OptionalAuth()} is more subtle: it is for routes that behave differently for a signed-in caller (for example, showing whether \emph{you} bookmarked an organisation) but must not break for an anonymous one, so a missing or invalid token is treated as "no user" rather than a 401. Finally, the guard distinguishes failure causes: a malformed or invalid token still returns 401, but an infrastructure error while reaching Supabase's JWKS endpoint returns 503 instead - deliberately, so that a transient network blip between the API and Supabase does not force-log-out every active session the way a blanket 401 would.

\section{Authorisation: Role-Based Access Control}
\label{sec:rbac-internals}
The \texttt{RolesGuard} reads \texttt{@Roles(...)} metadata attached to a handler and checks it against the roles \texttt{JwtGuard} already resolved onto the request. Matching is OR semantics - holding any one of the listed roles is enough - and a rejection names the specific role that was required, rather than a generic "forbidden", so a misconfigured client gets a diagnosable error instead of a silent 403. Organisation-level permissions go a layer deeper than the coarse volunteer/organisation/superadmin split: a team member's permission to publish content, review applicants or manage the team itself is checked against their \texttt{organization\_admins} row for that specific organisation, so the role check at the HTTP layer and the team-permission check at the service layer are deliberately separate concerns.

\section{Input Validation}
\label{sec:validation-internals}
A generic \texttt{ZodValidationPipe} wraps whichever Zod schema a route declares and runs before the handler body executes; a failure returns 400 with Zod's own field-by-field error list rather than a stack trace. Because the identical schema object is imported by both the NestJS route and the Expo client's \texttt{react-hook-form} resolver, the two sides cannot quietly drift apart the way hand-duplicated validation logic eventually does.

\section{Cross-Origin Resource Sharing}
\label{sec:cors-internals}
CORS is implemented as an origin-checking callback rather than a static allow-list, because a raw comma-separated string in the \texttt{Access-Control-Allow-Origin} header is invalid and silently rejected by browsers - the callback splits the configured origins and echoes back only the one that actually matches the request. In development, any \texttt{localhost} or \texttt{127.0.0.1} origin is allowed regardless of port, which works around Expo's dev server picking a different port on every run.

\section{SQL Injection Protection}
\label{sec:sql-injection}
Every ordinary query is built through Drizzle's parameterised query builder, which never concatenates caller-supplied values into SQL text. The one documented exception is a correlated subquery written inside a \texttt{select()} projection: Drizzle's usual \texttt{\$\{table.column\}} interpolation renders \emph{unqualified} in that specific position, so a hand-written, table-qualified SQL fragment is required there instead - a narrow, intentional trap flagged in the project's own engineering notes precisely because it is the one place a careless edit could reintroduce string-built SQL.

\section{Audit Logging}
\label{sec:audit-internals}
Administrative and other sensitive actions write an \texttt{audit\_logs} row capturing the actor, the action, the entity affected, a JSON snapshot of the value before and after the change, and the caller's IP address (Section~\ref{sec:impl-notifications}). The write is fire-and-forget - issued but never awaited inside the surrounding transaction - specifically so that a failure to write an audit record can never roll back or fail the business action it was meant to describe; losing an audit entry is an acceptable failure mode, losing a certificate issuance or a donation settlement is not. Deleting a user does not erase their history in the log: the foreign key from \texttt{audit\_logs} to \texttt{users} is \texttt{ON DELETE SET NULL} rather than cascading, so the historical record survives the account that produced it.

\section{Secrets Handling}
\label{sec:secrets}
Supabase's \texttt{service\_role} key - which bypasses row-level security entirely - is used only server-side and is never shipped to the client; the project's own setup documentation calls this out explicitly as the one credential that must never leak into a client bundle. Environment files are gitignored throughout the monorepo, and the automated test suite runs against throwaway values from a dedicated test environment file (Section~\ref{sec:testing-objectives}) rather than requiring a real \texttt{.env} to exist in CI at all.

\section{Known Gaps and Honest Limitations}
\label{sec:security-gaps}
Two things are deliberately not covered, and it would be misleading to imply otherwise. No \texttt{helmet}-equivalent middleware sets hardening headers (CSP, X-Frame-Options and similar) on API responses. And there is no server-side HTML sanitisation of user-submitted text; because the API is JSON-only rather than rendering HTML itself, stored-XSS risk is deferred entirely to the React/Expo client's own escaping behaviour rather than being neutralised at the boundary where the data is written. Both are reasonable gaps for the pilot's current scope, but a production hardening pass before handling data from untrusted public NGOs at scale should close them rather than assume the existing guards already do.

\chapter[Selected Implementation Deep-Dives]{Selected Implementation Deep-Dives}
\label{ch:deepdives}
Chapter~\ref{ch:implementation} gives the reader the crucial information about each module, and it is at this level that a reader should be able to understand the system; however in this chapter, five more complex pieces of business logic are described than can be adequately conveyed in a one-paragraph summary, and the correctness of the whole platform hinges on the correctness of these five components under concurrency and under adversarial input.

\section{Event Application Review: a Worked Transaction}
\label{sec:deepdive-events}
The review of an application is done within a single database transaction (reviewApplication). It first verifies that the caller is a member of the team it is given permission from and that they belong to the organisation that the team owns, and then it locks a row using \texttt{SELECT volunteers\_needed, accepted\_count FROM events WHERE id = ? FOR UPDATE} before any application is written; \texttt{WITHDRAWN} is a final state, and should not be reviewed again; a review that doesn't actually change the status is not a redundant write, it is a no-op; if you accept an application while \texttt{accepted\_count} is already at \texttt{volunteers\_needed} you will reject it (with a 409) before \texttt{accepted\_count} is incremented. Only once those pass does the application row update, and \texttt{accepted\_count} is adjusted by exactly $\pm 1$ - and only on an actual transition into or out of \texttt{ACCEPTED} - using \texttt{SET accepted\_count = GREATEST(accepted\_count + delta, 0)}. The \texttt{GREATEST(...,\,0)} floor is a defensive measure against the counter ever drifting negative, which would otherwise be possible if a review somehow executed its decrement twice.

\section{Need Pledge Review and a Deliberate Edge Case}
\label{sec:deepdive-needs}
Pledge review (\texttt{reviewPledge}) follows the identical lock-then-branch shape - \texttt{SELECT quantity, fulfilled\_quantity, status FROM needs WHERE id = ? FOR UPDATE} - but the business rule it enforces differs from the event case in a way worth stating precisely. A pledge's quantity is added to or subtracted from \texttt{fulfilled\_quantity} only when the pledge is in a "committed" state, which the implementation treats as \texttt{ACCEPTED} or \texttt{COMPLETED}; reaching \texttt{fulfilled\_quantity} $\geq$ \texttt{quantity} automatically flips the need's status to \texttt{FULFILLED}. The edge case: this automatic transition only ever runs OPEN$\to$FULFILLED. A need an organisation has manually set to \texttt{CLOSED} is never automatically reopened to \texttt{OPEN} by a later pledge rejection dropping the fulfilled count back down - closing a need is a one-way organisational decision the pledge-accounting logic does not get to override.

\section{Donation Settlement: the Checkout/Webhook Split}
\label{sec:deepdive-donations}
\texttt{createCheckout} only ever inserts a \texttt{PENDING} donation row with a server-computed \texttt{amountMinor}; nothing the client calls afterward is capable of marking a donation complete. \texttt{handleWebhook} is the only path that can, and it is written defensively at every step, as Figure~\ref{fig:webhook-idempotency} traces end to end: it looks the donation up by the provider's reference id and silently no-ops (logging only) if the donation is not still \texttt{PENDING}, which is what makes a duplicate webhook delivery harmless rather than a double-settlement. Before writing anything, it also verifies the webhook's reported amount against the donation's own \texttt{amountMinor} and rejects a mismatch with a 400 - a tamper check that runs before the settlement, not after.

\section{Feed Ranking: Three Scorers Over One Candidate Pool}
\label{sec:deepdive-feed}
All three ranked views - For You, Trending, Following - draw from one candidate pool, capped at 150 rows pulled across posts, events, needs and announcements together, and are scored in application code rather than in SQL. Table~\ref{tab:feed-scoring} breaks down the terms that make up \texttt{baseScore}, which For You and Following both build on.

\begin{table}[H]\centering

\begin{tabularx}{\textwidth}{|p{0.32\textwidth}|Y|}
\hline
\textbf{Term} & \textbf{Contribution}\\\hline

\noindent For You additionally subtracts 35 points from anything the viewer has already seen in the current session - a soft down-rank rather than a hard filter, so a seen item can still resurface rather than vanishing outright. Trending uses a different shape entirely:
\[
\text{trendingScore} \;=\; \frac{\text{engagement} \times 10}{(\text{age in hours} + 2)^{0.7}}
\]
a power-law decay rather than the linear one \texttt{baseScore} uses, and it weights location at only 20\% of its usual influence, since a trending view is explicitly meant to surface what the wider platform is engaging with, not just what is nearby. The heaviest weighting on applications and pledges in the engagement term is a deliberate product choice: a volunteer actually committing to help counts for far more in ranking than a like ever does. All three views are exposed to the volunteer as nothing more exotic than a lens switcher above the same home feed (Figure~\ref{fig:volunteer-home}), so none of this scoring machinery is visible as a separate screen - switching lenses re-queries the same candidate pool under a different score, and the card beneath a result renders identically regardless of which view surfaced it.

\section{Organisation Overview: Independent Parallel Queries}
\label{sec:deepdive-overview}
The organisation dashboard's summary numbers (Section~\ref{sec:impl-engagement}) come from \texttt{getMyOverview}, which issues its count queries as independent \texttt{Promise.all} calls rather than one sequential chain - published events, open needs, pending applications, and, separately, the \emph{distinct count of events} those pending applications span, with the same pair repeated for pledges and needs. The distinction is deliberate: an organisation coordinator reading "47 pending applications" needs to know separately whether that is 47 people applying to one event or spread thinly across twelve, and the dashboard answers both questions rather than forcing a drill-down to find out. \noindent \\ \\ Every one of these numbers renders as a plain stat tile rather than a chart, for the same reason the superadmin overview does (Section~\ref{sec:impl-admin-console}): a point-in-time count has no second axis to plot against, and the one place either dashboard draws an actual line is the superadmin trend chart, because a day-by-day series is the one number here with a dimension worth showing visually.

\section{Partial Unique Indexes for State-Scoped Uniqueness}
\label{sec:deepdive-partial-unique}
A plain unique constraint says a column (or column pair) can never repeat across the whole table's history; several of Nabhya's rules instead say it can never repeat \emph{while a row is in a particular state}, which is a different and strictly weaker guarantee that PostgreSQL expresses as a unique index with a \texttt{WHERE} clause rather than as a table-wide constraint. \texttt{organization\_admins} carries three such indexes, all scoped to \texttt{status = 'ACTIVE'}: one active membership per \texttt{(organization\_id, user\_id)}, one active \texttt{OWNER} per organisation, and one active owner-role membership per user, so a removed or left member's historical row never blocks that same person from rejoining later. \noindent \\ \\ \texttt{team\_invites} and \texttt{organization\_ownership\_transfers} use the identical technique scoped to \texttt{status = 'PENDING'}: an organisation can have at most one pending invite per email and at most one pending ownership transfer in flight at a time, but as many \texttt{ACCEPTED}, \texttt{EXPIRED} or \texttt{REJECTED} rows in its history as it likes.
\noindent \\ \\ The alternative - enforcing this in application code with a \texttt{SELECT} before every \texttt{INSERT} - has a race window between the check and the write that a partial index closes at the database level regardless of how many requests arrive concurrently.

\clearpage

\section{Polymorphic Target References Without Foreign Keys}
\label{sec:deepdive-polymorphic}
\texttt{post\_interactions}, \texttt{post\_comments}, \texttt{notifications} and \texttt{audit\_logs} each need to point at a row that could belong to any one of several different tables - a like can land on a post, an event or a need; a notification's \texttt{entity\_id} might be an application, a certificate or a donation. A database foreign key can only ever reference one named table, so these columns are deliberately left as plain UUIDs with an accompanying \texttt{target\_type} (or, for audit and notification rows, an implied type carried by the \texttt{action}/\texttt{type} enum) rather than as foreign keys, and the API resolves and authorises the referenced row itself before trusting the pointer. This is a standard trade-off for a polymorphic association: the schema cannot stop an orphaned or mistyped reference the way a foreign key would, so the service layer is where that check has to live instead, and Section~\ref{sec:erd} calls this out at each table rather than presenting the missing foreign keys as an oversight in the ER diagrams.

\chapter{Conclusion}
\label{ch:conclusion}

To sum up, Nabhya is a mobile-first solution that integrates NGO verification, volunteer opportunities, item-level giving and engagement and verifiable participation certificates. One of them consists of an Expo app that calls a REST API, built with NestJS and Supabase Auth for authentication, while Supabase Storage and shared Zod contracts reside side by side with Supabase PostgreSQL database, handled with the help of Drizzle ORM. The privileges of volunteers, organisations and superadmins differ, and anonymous visitors can view only some public information and verify certificates.

\noindent \newline Most of the engineering decisions come down to trust and doing the right thing. Organisation documents are reviewed before an organisation becomes public, and public listings only display verified and active organisations. Event capacity and need fulfilment counters are updated inside transactions, and important relationships are preserved through database uniqueness constraints. Payments settle only through signature-verified webhooks, and files move only through short-lived signed URLs. The integration tests (Chapter~\ref{ch:testing}) exercise a PostgreSQL-compatible database that we construct from the committed migrations.

\noindent \newline  The project is also clearly bounded (Section~\ref{sec:limitations}). The web console and email and push notifications are yet to be built, full client pagination is still pending, and monetary donations are on hold until go-live. Real-world adoption and performance have not been demonstrated yet, and this should be done with field studies and validated measurements (Section~\ref{sec:future}). In this limited sense, Nabhya gives us a sufficient base for more reliable and effective giving.

\chapter{Developer Setup Guide}
\label{app:setup}
\label{sec:setup-guide}
This appendix is the exact sequence used to stand up a new development environment, taken from the project's own \texttt{README.md} and the interactive setup wizard in \texttt{scripts/}, together with the gotchas already documented in the project's engineering notes.

\begin{enumerate}[itemsep=0.15em, topsep=0.25em, parsep=0.1em]
  \item At the root of the repository, run \texttt{pnpm install} - which will install all workspaces in a single command.
 \item Create a Supabase project. The remote JWKS endpoint the API validates against (Section~\ref{sec:jwt-internals}) requires asymmetric JWT signing; it is not required in the old shared-secret mode. Turn off Confirm email'', as there is no email provider hooked up. Copy the session pooler connection string (port 5432), not the Direct connection'' string, which is IPv6-only and requires the paid IPv4 add-on. 
  \item Copy the Project URL and the anon key for the client, and the \texttt{service\_\allowbreak role} key for the server only -- Section~\ref{sec:secrets} explains why the \texttt{service\_\allowbreak role} key should never be sent to a client\allowbreak{} bundle.
  \item Populate \texttt{apps/\allowbreak server/\allowbreak .env} and \texttt{apps/\allowbreak native/\allowbreak .env.local} - two different files for two different apps, which is the single easiest step to mix up. Running \texttt{pnpm db:setup} runs an interactive wizard that writes both correctly instead.
  \item Run \texttt{pnpm db:push} to apply the schema, then \texttt{pnpm --filter\allowbreak\ @nabhya/db\allowbreak\ db:seed} to seed the three roles and ten categories. The seed script reads its environment relative to its own directory, so source \texttt{apps/\allowbreak server/\allowbreak .env} first (\texttt{set -a;\allowbreak\ source\allowbreak\ apps/\allowbreak server/\allowbreak .env;\allowbreak\ set +a}) to avoid a silent failure.
  \item Start the API with \texttt{pnpm --filter\allowbreak\ server dev} (serves on port 3000, with Swagger documentation at \texttt{/api/\allowbreak docs}) and the mobile app with \texttt{pnpm dev} inside \texttt{apps/\allowbreak native}, or run \texttt{pnpm dev} from the repository root to start both together through Turborepo.
\end{enumerate}

\noindent Three gotchas cost debugging time if missed. First, \texttt{drizzle-kit push} - not a tracked migration - still runs on every non-production boot, so a migration file alone changes nothing until \texttt{db:push} runs. Second, there is no HTTP route to mint the first superadmin by design (\texttt{AdminService.\allowbreak grantSuperadmin} is never routed); grant it by script or by editing \texttt{user\_roles} directly. Third, run \texttt{pnpm --filter\allowbreak\ server\allowbreak\ verify:di} after touching any constructor - the build tool emits no decorator metadata, so a missing \texttt{@Inject} can silently leave a service with an undefined dependency that only surfaces as a 500, not at boot.

\chapter{Glossary}
\label{app:glossary}
This glossary defines terms as they are specifically used inside Nabhya's codebase and this report, where that usage is narrower or more specific than the generic industry term.

\begin{longtable}{|p{0.22\textwidth}|>{\raggedright\arraybackslash}p{0.68\textwidth}|}
\caption{Glossary of project-specific terms.}\\\hline
\textbf{Term} & \textbf{Definition in this project}\\\hline
\endfirsthead\hline\textbf{Term} & \textbf{Definition in this project}\\\hline\endhead
Candidate pool & The up-to-150-row set of posts, events, needs and announcements pulled before feed ranking scores and diversifies them (Section~\ref{sec:deepdive-feed})\\\hline
Committed pledge & A need pledge in the \texttt{ACCEPTED} or \texttt{COMPLETED} state - the only states that count towards a need's \texttt{fulfilled\_quantity} (Section~\ref{sec:deepdive-needs})\\\hline
Denormalised counter & A column such as \texttt{events.accepted\_count} or \texttt{needs.fulfilled\_quantity} that caches an aggregate so the public API never has to run it live; kept correct only by updating it inside the same locked transaction as the row that changes it\\\hline
Deny-by-default & The API's baseline posture: every route requires a valid, non-suspended session unless explicitly marked \texttt{@Public()} or \texttt{@OptionalAuth()} (Section~\ref{sec:guard-pipeline})\\\hline
Fire-and-forget & An operation - specifically audit logging - issued without being awaited, so its own failure cannot roll back or fail the action it is recording (Section~\ref{sec:audit-internals})\\\hline
JIT user sync & Creating or linking a local \texttt{users} row the first time a verified Supabase identity is seen, rather than provisioning it at a separate signup step (Section~\ref{sec:jwt-internals})\\\hline
Need & An organisation's item-level listing, either a WANT (something it needs) or an OFFER (surplus it is giving away) - the platform's differentiator from a pure volunteering/event listing\\\hline
Partial unique index & A uniqueness constraint scoped by a \texttt{WHERE} clause, used throughout \texttt{organizations.ts} so that, for example, only one \emph{active} team membership can exist per user-organisation pair while historical \texttt{REMOVED} rows are not constrained against it\\\hline
Row lock & \texttt{SELECT ... FOR UPDATE} taken on a parent row (an event or a need) before its denormalised counter is read and written, preventing two concurrent reviews from both reading a stale count\\\hline
Signed URL & A short-lived, pre-authorised URL issued by the API that lets the client upload to or download from Supabase Storage directly, without the file ever passing through the API server\\\hline
Soft revoke & A certificate's \texttt{revoked\_at}/\texttt{revoked\_reason} fields marking it invalid without deleting the row - the public verification endpoint still resolves a revoked certificate, but marks it void rather than returning not-found\\\hline
Team permission & An organisation-scoped capability (such as \texttt{content.publish} or \texttt{people.review}) checked against a team member's \texttt{organization\_admins} row, layered underneath the coarser volunteer/organisation/superadmin role check (Section~\ref{sec:rbac-internals})\\\hline
WANT/OFFER & The two \texttt{needs.type} values - a request for something versus a surplus being given away - sharing one schema and one set of endpoints rather than being modelled as separate features\\\hline
\end{longtable}
